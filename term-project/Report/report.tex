\section{Rationale}
\label{sec:rationale}

Every frame of a real-time 3D application starts the same way: the CPU assembles a
list of rendering commands and hands them to the GPU one at a time. Each of those
submissions is a \emph{draw call}. Modern GPUs are massively parallel, but the work
of preparing and issuing a draw call stays largely serial on the CPU side, covering
state validation, driver translation, and command-buffer encoding. Once a scene holds
thousands of objects that share a mesh and a material (a common situation in
open-world games, crowd simulations, and procedurally generated environments), the
CPU turns into the bottleneck. The cause is not computational complexity; it is the
sheer volume of commands that must be submitted every frame.

This bottleneck is well documented by industry practitioners. At GDC 2011,
Pranckevi\v{c}ius~\cite{aras2011batch} showed that even on the hardware of the day a
practical real-time budget sat around 1\,000--3\,000 draw calls per frame at 60\,FPS
on console. Go past that budget and the CPU starves the GPU, which then idles between
batches while the frame rate falls. The problem has only become more pressing since:
contemporary open-world titles routinely place tens of thousands of environmental
props (trees, rocks, grass blades) inside a single view frustum.

Unity's Built-in Render Pipeline offers two standard ways to soften this cost.
\textbf{GPU Instancing}~\cite{unitygpuinstancing} collapses every draw call for
objects that share a mesh and an instancing-enabled material into a single batched
call, passing the per-instance transform data in a GPU-side buffer. CPU overhead then
scales with the number of \emph{batches}, bounded by the driver's maximum instance
count per call, rather than with~$N$. \textbf{Static Batching}~\cite{unitybatching}
attacks the same problem from the other side: at scene load it merges the mesh data of
all participating objects into one large combined mesh and issues a single draw call
over the whole geometry. Per-object command overhead disappears, but the vertex data
of every instance is duplicated in memory.

The choice between the two is not academic. A Unity Discussions thread on batching
trade-offs~\cite{unityforum2019} notes that Static Batching's mesh merging adds runtime
memory overhead and lengthens startup, while GPU Instancing can place more load on the
CPU than developers expect, so the better option is platform-dependent and should be
confirmed by profiling rather than assumed. The Unity blog on the SRP
Batcher~\cite{unitysrpbatcher} is careful to note that the Built-in Pipeline mechanisms
studied here behave differently from the newer SRP Batcher.
Akenine-M\"oller et al.~\cite{realtimerendering} add a further caveat: on tile-based GPU
architectures, which include mobile and Apple Silicon SoCs, the gains from draw-call
reduction can be partly cancelled out by extra vertex-fetch pressure when the geometry
is large. This study quantifies both strategies on an Apple Silicon Metal backend, so
its data speaks directly to developers targeting the macOS and iOS gaming market.

\section{Experiment Design}
\label{sec:design}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{../scene.png}
  \caption{Test scene overview.}
  \label{fig:scene}
\end{figure}

\subsection{Scene and Apparatus}

All measurements were taken in a dedicated Unity 2022.3.62f3 scene
(\texttt{InstancingBenchmark.unity}) on an Apple Silicon MacBook with the Metal
graphics backend. The scene holds one directional light with shadows disabled, a
top-down perspective camera at $(0,\,160,\,0)$ with $90^\circ$ pitch and FOV~$70^\circ$
(its frustum reaches $\pm105$\,units, comfortably enclosing the widest grid at
$\pm75$\,units), and a runtime-spawned square grid of spheres at $y=0$ with 1.5-unit
spacing. Physics, animations, post-processing, shadows, and VSync were all switched off,
and \texttt{Application.targetFrameRate} was set to $-1$ so the frame rate ran
unconstrained.

\subsubsection{Why the Test Scene Is Deliberately Minimal}

The scene is intentionally bare, and that is a design choice rather than an oversight.
Physics, skeletal animation, and post-processing each carry their own CPU cost, and on a
unified-memory machine they also draw on the same RAM pool the renderer uses. Folding
them in would mean the per-frame budget is no longer governed by draw-call submission,
so a shift in frame time could no longer be attributed cleanly to the rendering mode
under test. Reducing the scene to a static grid of identical spheres leaves the
draw-call path as the only thing that changes between configurations, and that is
exactly what keeps the 45-way comparison interpretable. The cost of a richer, more
game-like frame is acknowledged separately in Section~\ref{sec:limitations}.

\subsubsection{Deviations from the Phase-I Plan}

The following changes were made relative to the Phase-I submission to strengthen the
experimental design:

\begin{itemize}
  \item \textbf{Third rendering mode added.} Phase I described only Baseline and GPU
        Instancing. Static Batching was added because it is the primary alternative
        optimisation in Unity's Built-in Pipeline and supplies an essential reference
        point for the memory/batch-count trade-off.
  \item \textbf{Procedural UV spheres instead of imported assets.} Asset meshes bring
        uncontrolled vertex and triangle counts and licensing constraints. Procedural
        spheres give exact, logged geometry counts and are fully reproducible without
        any external package.
  \item \textbf{Mesh complexity as a second independent variable.} Three subdivision
        tiers (Low, Mid, High) isolate the effect of GPU vertex load independently of
        the draw-call count, which exposes the CPU-bound to GPU-bound transition.
  \item \textbf{Total configurations grew from 10 to 45} ($5\ N \times 3$ complexity
        $\times\ 3$ modes), and each configuration is repeated three times for
        statistical reliability.
\end{itemize}

\subsubsection{Rendering Modes}

\textbf{Baseline.} Each object uses a Standard shader material with
\textit{Enable GPU Instancing} unchecked. Unity issues one draw call per visible
object, reproducing the worst-case unoptimised scenario.

\textbf{GPU Instancing.} The same geometry is rendered with a second material that has
\textit{Enable GPU Instancing} enabled. Unity groups objects sharing a mesh and
material into instanced draw calls. On the Metal backend the maximum instance count
per call is roughly 500, so $N$ objects produce $\lceil N/500 \rceil$ instanced batches
plus a small fixed overhead (typically 1--2 calls for camera and lighting).

\textbf{Static Batching.} Objects use the Baseline material, and
\texttt{StaticBatchingUtility.Combine} is called at runtime to merge all meshes into a
single combined mesh. Unity then issues draw calls sized by its internal
65\,536-vertex combined-mesh limit (the manual rounds this to ``64{,}000'', but the
true boundary is the $2^{16}$ 16-bit index-buffer limit), so the expected batch count
is $\lceil N \cdot v / 65\,536 \rceil$, where $v$ is the per-object vertex count. For
low-poly objects this approaches 1; for high-poly objects it can climb to or past the
Baseline count.

\textbf{Dynamic Batching} was left out because Unity restricts it to meshes with at
most 300 vertices, a limit only the Low-poly tier satisfies. Including it would have
produced incomplete data for the Mid and High tiers and biased the comparison.

\subsection{Dependent Variables}

\begin{itemize}
  \item \textbf{FPS average} -- mean of $1/\Delta t_{\text{unscaled}}$ over the
        measurement window.
  \item \textbf{FPS 1\% low} -- mean of the bottom 1\% of per-frame FPS samples,
        capturing worst-case hitches.
  \item \textbf{Wall-clock frame time (ms)} -- mean of
        $\Delta t_{\text{unscaled}} \times 1000$, the full frame-to-frame duration the
        player actually experiences, including the GPU synchronisation latency the
        Metal driver absorbs (see Section~\ref{sec:crossvalidation}).
  \item \textbf{GPU frame time (ms)} -- mean of \texttt{FrameTimingManager.gpuFrameTime}
        sampled once per frame, with zero samples discarded so they do not bias the
        mean.
  \item \textbf{Draw call batches} -- median of the \texttt{Batches Count}
        \texttt{ProfilerRecorder} sampled once per frame. Where the Metal counter
        returned zero, the theoretical value is substituted
        (Section~\ref{sec:methodology}).
  \item \textbf{Total Reserved Memory (MB)} -- mean of the
        \texttt{ProfilerCategory.Memory} ``Total Reserved Memory'' counter, capturing
        the per-configuration memory footprint including the Static Batching combined
        mesh.
\end{itemize}

\subsection{Control Variables}

Camera position and orientation, lighting configuration, screen resolution
($1920\times1080$), object grid layout, sphere scale, and the hardware environment
(Apple Silicon MacBook, Metal API) were held constant across all 45 configurations.
Each configuration was measured three times (\texttt{repeats}~$= 3$). A 3-second
warm-up, during which \texttt{FrameTimingManager.CaptureFrameTimings()} was called
every frame to prime the Metal driver's GPU-timing pipeline, was discarded ahead of
each 30-second measurement window. Per-frame GPU timing samples of zero were excluded
from the mean to avoid a downward bias during driver initialisation.

\section{Methodology}
\label{sec:methodology}

\subsection{Automated Benchmark Harness}

A \texttt{BenchmarkRunner} MonoBehaviour iterates over all 45 configurations in a Unity
coroutine, repeating each three times for 135 measurement windows in total. For each
window it calls \texttt{BenchmarkSpawner.Spawn()}, waits 3\,s for warm-up, records
metrics frame-by-frame for 30\,s, then calls \texttt{BenchmarkSpawner.Clear()} followed
by \texttt{System.GC.Collect()} and \texttt{Resources.\allowbreak UnloadUnusedAssets()} to release
the Static Batching combined mesh before moving on. A full run takes about 75 minutes;
one row per repeat is written to a timestamped CSV under \texttt{BenchmarkResults/}, and
a Python script aggregates the means and standard deviations.

Frame time is sampled via \texttt{Time.unscaledDeltaTime}; GPU time via
\texttt{FrameTimingManager.\allowbreak GetLatestTimings}, with zero-valued samples from driver
initialisation discarded; batch count via a \texttt{ProfilerRecorder} on
\texttt{Batches Count}; and memory via the \texttt{Total Reserved},
\texttt{Gfx Reserved}, and \texttt{GC Reserved} memory recorders. On Metal the
\texttt{Batches Count} recorder intermittently returns zero. For those cases the
analysis script substitutes the theoretical formula ($N{+}1$ for Baseline,
$\lceil N/500 \rceil$ for GPU Instancing, $\lceil N \cdot v / 65\,536 \rceil$ for
Static Batching). The \texttt{SetPass Calls Count} recorder consistently returned 2
regardless of mode or $N$, which was confirmed in the Game-window Statistics overlay
(Section~\ref{sec:statsval}), so it is excluded from the CSV.

\label{sec:crossvalidation}

(Window $\to$ Analysis $\to$ Profiler) to validate the harness.

The GPU Instancing $N$=10\,000 High row exposes the binding constraint at high mesh
complexity. The Profiler shows 66.2\,ms of CPU frame time, almost all of it inside
\texttt{Gfx.WaitForPresentOnGfxThread} (62.8\,ms). The main thread submits the 21
instanced draw calls in only about 3\,ms, but the game loop cannot start a new frame
until the GPU has finished presenting the previous one. Rendering roughly 198 million
triangles takes the GPU about 66\,ms, and that stall is absorbed into
\texttt{Time.unscaledDeltaTime} while also surfacing inside
\texttt{Gfx.WaitForPresentOnGfxThread} in the Profiler timeline, so harness and
Profiler agree to within 0.5\,ms. This confirms that wall-clock frame time
(\texttt{Time.unscaledDeltaTime}) is the right player-facing metric: it consistently
matches Profiler $\text{Main Thread} + \text{Wait-for-Present}$ across both CPU-bound
and GPU-bound regimes, whereas the GPU-side cost itself is invisible to the Profiler's
GPU module on Metal and has to be read from \texttt{FrameTimingManager}.

\section{Discussion}
\label{sec:discussion}

\subsection{Draw-Call Reduction and CPU Relief}

The primary hypothesis holds: at large $N$ with low- or mid-poly meshes, GPU Instancing
cuts draw calls from $O(N)$ to $O(N/500)$ and measurably lowers the wall-clock frame
time. At $N=10\,000$ low-poly the frame time drops from 8.80\,ms under Baseline to
3.64\,ms under GPU Instancing, a 59\% reduction. Static Batching with low-poly meshes
posts the best absolute frame rate (365\,FPS at $N=10\,000$), because its combined-mesh
batching is most efficient when the per-object vertex count is small enough to pack
many objects into a single 65\,536-vertex chunk.

\subsection{CPU-Bound to GPU-Bound Transition}

At high mesh complexity and large $N$ the bottleneck moves from the CPU, where
draw-call overhead dominates, to the GPU, where vertex and fragment processing dominate.
At $N=10\,000$ high-poly the wall-clock frame times are 79.1\,ms (Baseline), 65.7\,ms
(GPU Instancing), and 69.0\,ms (Static Batching): the three values fall within roughly
20\% of one another, a clear sign that the GPU is close to fully saturated. GPU
Instancing's draw-call advantage still buys a 17\% frame-time improvement over Baseline
(65.7 vs 79.1\,ms), but that margin is far narrower than in CPU-bound configurations,
where the speedup exceeds $2\times$. The same transition shows up in both the scatter
plot (Figure~\ref{fig:scatter}) and the bar chart (Figure~\ref{fig:bar}): as complexity
and $N$ grow, the GPU frame time approaches the wall-clock frame time.

\subsection{Static Batching: Batch-Count and Memory Trade-off}
\label{sec:memtrade}

Static Batching wins on frame rate only while the combined mesh fits into very few
65\,536-vertex chunks. At $N=10\,000$ high-poly it issues 1\,668 batches and the
optimisation is all but nullified. Table~\ref{tab:staticbatch} breaks down the
theoretical $\lceil N \cdot v / 65\,536 \rceil$ against the measured batch counts: the
steady $+1$ to $+2$ excess is fixed camera/lighting overhead, while the $+157$ excess
at high-poly $N=10\,000$ reflects index-buffer overhead at the vertex-limit boundary.

Memory is the second half of the trade-off (Figure~\ref{fig:memory}). At $N=10\,000$
high-poly, Static Batching reserves about 6\,200\,MB, a 4.5$\times$ overhead against the
roughly 1\,265--1\,380\,MB of Baseline and GPU Instancing, because
$10\,000 \times 9\,902 \approx 99$~million vertices are duplicated in the CPU-side
combined mesh. The practical guideline that follows is straightforward: use Static
Batching for low-poly-heavy scenes such as foliage and small props, where the combined
mesh stays compact, and treat GPU Instancing as the robust default for high-poly
objects or for $N\gtrsim 5\,000$.

\subsection{Apple Silicon Unified Memory Note}

On Apple Silicon the unified-memory architecture means the GPU-side pressure from the
Static Batching combined mesh competes directly with CPU memory. That is a meaningful
difference from discrete-GPU systems, where a separate VRAM pool exists, and it is the
reason the 4.5$\times$ memory cost above matters in practice rather than being absorbed
silently into a dedicated VRAM budget.

\section{Limitations}
\label{sec:limitations}

A few limitations bound how far these conclusions can be carried:

\begin{itemize}
  \item \textbf{Single platform.} All measurements were taken on Apple Silicon Metal.
        The D3D11 and Vulkan backends may show different batch-count saturation points
        and different GPU synchronisation behaviour.
  \item \textbf{Built-in Render Pipeline only.} URP, HDRP, and the SRP Batcher use
        fundamentally different batching mechanisms and are out of scope here.
  \item \textbf{No overdraw, no shadows, no post-processing.} The top-down opaque grid
        isolates the draw-call effect cleanly but is not representative of a full game
        frame, in which fragment cost would be far higher.
  \item \textbf{No animation, physics, or audio.} As explained in
        Section~\ref{sec:design}, removing these systems keeps the frame budget
        dominated by rendering, which is what the experiment needs. A real game carries
        additional CPU load that would shift the CPU/GPU balance, and quantifying that
        shift is left to future work.
  \item \textbf{Fixed camera, no frustum culling exercise.} Every object stays inside
        the frustum, so the per-object culling savings of GPU Instancing, which can
        skip culled instances, were not measured against Static Batching's
        all-or-nothing combined mesh.
  \item \textbf{Editor-mode measurement.} Cross-validation showed harness and Profiler
        agreement within 0.5\,ms, so any EditorLoop overhead is sub-millisecond on this
        hardware.
\end{itemize}

\section{Conclusion}
\label{sec:conclusion}

This study measured the performance impact of GPU Instancing and Static Batching across
135 measurement windows (45 configurations $\times$ 3 repeats) spanning five object
counts, three mesh complexities, and three rendering modes on Apple Silicon Metal.

The key findings are:
\begin{enumerate}
  \item \textbf{GPU Instancing} reliably reduces draw calls to $\lceil N/500 \rceil$
        batches regardless of mesh complexity, and delivers significant frame-time
        savings while the scene is CPU-bound. Once mesh complexity and $N$ are high
        enough for the GPU to become the binding constraint, the benefit narrows to
        17\% at $N=10\,000$ High, against roughly 59\% at $N=10\,000$ Low.
  \item \textbf{Static Batching} beats GPU Instancing for low-poly objects but degrades
        sharply with mesh complexity because of Unity's 65\,536-vertex combined-mesh
        limit. At high-poly with $N=10\,000$ it gives almost no benefit over the
        unoptimised Baseline and consumes 4.5$\times$ more memory.
  \item Under \textbf{GPU-bound} conditions, all three modes converge toward comparable
        wall-clock frame times, which confirms that draw-call optimisation pays off
        only while the CPU is the bottleneck.
\end{enumerate}

For developers targeting Apple Silicon or other tile-based GPU architectures, GPU
Instancing is the recommended default for scenes with many identical objects. Static
Batching stays viable for low-poly-heavy scenes, but it has to be weighed against its
memory cost and its vertex-count scaling behaviour.
